## Look back / right-stick camera (user request 2026-11-06)

- Research 2026-11-07: no public Gecko code, Tournament Edition note or manual entry for a look-back button was
  found (web searches on Tournament Edition controls and on Sonic Riders camera codes) [uncertain: TE's own
  Discord/docs not checked]. The original game has no look-back input.
- Known: camera block 0x81A05D74 (0x38 per viewport; eye +0x14, target +0x20), view matrix 0x81A0583C; the
  writer is not found yet (notes/game-addresses.md).
- Plan A (render-only, online-safe): while the button is held, turn view space 180 degrees around the
  camera's up axis (x and z negated) for perspective draws in gx.vert, and mirror nothing else. Problem to
  check first: the game culls objects outside its own view, so what is behind the camera may not be drawn
  at all. Test: hold the button on the det route and look at the frame.
- Plan B (game-side): find the camera writer (watch 0x81A05D74+0x20 with `SR_WATCH`), then on the button swap
  the target to the mirror of the eye (target' = 2*eye - target) after the game wrote it. The game then
  culls for the new view. Changes game memory: online sessions must send the button with the inputs
  (lockstep already sends pads; the C-stick is part of the pad).
- Mapping: right stick / C-stick down = look back (Android already maps the right stick to the C-stick);
  keyboard: a free key. Option in the Controls tab.

## Nitrous-style boost toggle (user request 2026-11-07)

Wanted: an option where **holding B** keeps boosting like nitrous and uses air for as long as B is held; a
normal **tap** of B behaves exactly as now, even with the option on.

- Needed from the game: per player (array 0x81A0D740, 0x1080 each) the boost timer/state, the air value and
  the gear's boost cost (gear table 0x819EA240, level blocks). Find them with RAM dumps: before / during /
  after a boost on the det route (`SR_RAMDUMPAT`), words that change exactly at the boost.
- Behaviour: when the game's boost ends and B is still held (held longer than one boost), start it again
  or hold its timer, and take air at boost cost / boost length per frame; stop when B is released or the air
  runs out (then the normal "no air" behaviour). A tap never reaches the hold path, so it is unchanged.
- Runs once per game step (game_mods.c, like the Chaos Emerald byte). It changes game memory: in online
  sessions the host's setting must apply to everyone (send it in the welcome, as the camera aspect) or the
  option is off online.
- Default off; Gameplay tab.

## Windowed launcher / installer (user request 2026-11-07)

- Reference: SwitchWakerHD's installer (`installer/desktop`, C# Avalonia: one window app for Windows, macOS and
  Linux; `installer/shared` engine; Spanish/English/Portuguese strings; it downloads its own pinned Python and
  tools, asks for the disc, the SD card, the optional HOME icon with prod.keys and copies with read-back
  checks). License MPL-2.0: we may study it; copying files means keeping them MPL with notices.
- Our plan: a small window app in front of the existing setup engines (setup.ps1 on Windows,
  tools/setup_linux.py on Linux/Deck): pick disc, targets (Switch / PC / Android / Linux), SD card, HOME icon
  (keys + picture), progress bar from the engine's step lines, log button, "open folder" at the end. Options:
  (a) Python + Tk (already shipped Python; plain look unless themed), (b) Avalonia like SWHD (best look, needs
  .NET publish per OS, signing questions), (c) a local web page served by the setup's Python (any look,
  opens in the browser). Recommendation: (c) or (a) first, since both reuse the shipped Python; decide with
  the user (mockups).

## Ideas from Tag Force Recomp (user tip, 2026-11-07; studied from its release docs)
github.com/Artknighty/tagforcerecomp-preview: a PSP static recomp to Windows (MIPS to C, HLE kernel, GE on the GPU).

**How its launcher works.** The release zip holds a ready-made `TagForceRecomp.exe` with **no game code in it**,
plus the translator, TinyCC and FFmpeg. The exe opens as a launcher: "Select ISO...", then "Install and play"
(copies the game files, translates the game's code on the player's PC into `gen/`, TinyCC compiles it in seconds
into `gen/jitcache/`, loaded into memory at each start; the ISO is not needed afterwards), later just "Play".
Nothing to install, no toolchain download. Pages: Game (options), Controls (remap by pressing a key/button),
Mods (on/off + order), Cheats. Also `--install <iso>`, `--verify <iso>`.

**What we can take, by size:**
1. Small, in our existing ImGui menu: button remapping by pressing (ours: fixed layout, text only); mod order
   up/down (ours: on/off only); hotkeys (F3 FPS counter, F4 frame rate, F8 report a problem; Esc asks before
   closing); every session keeps its log + input recording (our SR_RECORD) + a save copy in `logs/` (last N),
   so a bug report can be replayed; a Cheats tab (unlock everything: `online_unlock` exists; Chaos Emerald).
2. Medium: a launcher window in front of setup (plans above), using our own ImGui + SDL instead of Tk/Avalonia:
   same look as the in-game menu. It still needs a toolchain to build, as today.
3. Large (the real lesson): split the PC build into a **prebuilt runtime exe** (runtime + ImGui + renderer, no
   game code, can ship ready-made) and a **game-code DLL** built on the player's PC. The shipped exe is then the
   launcher: pick the disc, "Install and play" (dtk split + recompile + compile the DLL, progress bar), "Play".
   Settings pages = the in-game menu tabs. Switch/Android keep the current build (no compiler on the device).
4. TinyCC instead of llvm-mingw (PC only): would make the first run seconds and drop the ~300 MB download, but
   our generated code is ~770k lines / 58 MB and needs musttail, bswap and always_inline stand-ins; TinyCC does
   not optimize, and our game thread is ~2 ms/step at -O2, so maybe 10-20 ms (too close to 16.7). Floating-point
   code generation must also stay bit-identical for online play. An experiment, not a plan.
